# Weave Web, stage 2: the node in the browser, with a storage node

The plan in OVb4TP5x had two stages: first a hosted node per person, later a node in the browser. martl decided (6.11.2026) to go straight to the second, with fixed nodes taking the place keepers had: a browser's node holds the keys and reads, and a storage node the person chose holds their spaces without being able to read them.

## Why not keepers again

Keepers were taken out on 6.11.2026 (docs/v2-stage5.md) for three reasons, and a storage node answers each:

- Nobody agreed to what was on their disk: a storage node offers storage, and a person chooses it.
- A deletion couldn't reach a keeper who was offline: a storage node is always on.
- Copies of abandoned accounts stayed: a storage node knows its accounts, so a deletion and a time limit reach everything.

It isn't a friend's computer and it isn't chosen at random. Nothing in it is offered to, or taken from, friends.

## The shape

```
browser (a Worker)                 storage node (fixed, always on)             everyone else
keys, reading, signing   ──wss──▶  auth keys and topics, no keys      ◀──DHT──▶ peers
storage in OPFS                    sealed events, blobs, a quota
PeerSession2                       PeerSession2                                 PeerSession2
```

**The browser is not on the DHT.** It needs no relay: it speaks PeerSession2 to its storage node over a WebSocket, and the storage node is on the DHT. That takes `@hyperswarm/dht-relay` out of the plan.

**Blind holding (built, `HeldSpace.blind`).** Sync never needed a space's key, only what comes from it through a hash:

- `authKey(key)` proves the space to a peer (the tag is an HMAC under it);
- `topicOfKey(key)` is where the space's peers meet;
- the events travel sealed, and a Replica checks their signatures without opening them.

So a person hands their storage node one auth key and one topic per key of a space. With those it finds the peers, takes the events and passes them on, and can't open one. `packages/node/test/blindholder.test.ts`: it carries a space between two people who are never online together; it holds no plaintext; the auth key of another space gets it nothing.

**When a key rotates** while the tab is closed, the holder falls behind: it holds only the old auth key, so it gets no new events of that space until the person's browser comes back, takes the new key from a peer and hands on the new auth key. It is tested. That is the price of not holding the key: a space that rotated waits for one visit.

**What a storage node sees:** which account it serves, which spaces by id, the events' envelopes (who signed, when, how large, and the class of event) and how much is stored. Any member's device sees that much too, but here it is one operator and it knows the account. This goes in the privacy policy.

**What it can't do:** read a sealed event or sign one. Public events it can read, as anyone can. A person can leave it by telling it to delete, and the auth keys it held open nothing.

**What a browser still has to trust:** the JavaScript it is served. Whoever controls martl.io could serve code that reads the keys. Strict CSP, no third-party scripts and builds from release tags with published hashes make that checkable, not impossible.

## What is left

In order, each one usable and tested before the next:

1. **Blind holding:** done.
2. **PeerSession2 over a WebSocket:** done (`packages/net/src/wspeer.ts`, `@weave/net/browser`, `packages/node/test/wspeer.test.ts`). A session now needs only a `PeerStream`. TLS gives no handshake hash a page can read, so the two ends agree on one with fresh X25519 keys: whoever sits in between has a different hash on each side, and a tag seen on one connection is worth nothing on another. It authenticates nobody, and it isn't encryption: who may connect is step 3's, and privacy on the way is TLS's and the seals'. A long message goes as several frames, so the 1 MB limit of `websocket.ts` doesn't break images. Tested between a real server and a real client, not yet from a page in a browser.
3. **Storage node service:** the core is done (`packages/node/src/storagenode.ts`, the client in `packages/net/src/storageclient.ts`; `storagenode.test.ts`, and `storageswarm.test.ts` on a DHT testnet).
   - Accounts by invitation (one use, only a hash kept). An account's id is a key of its own, not the person's identity, so the node needn't know who it serves.
   - **No WebAuthn on the server.** A token only the person can make (from their passkey's PRF value, or their words) finds a sealed box with their keys, and the node keeps its hash. A passkey never talks to the node. Wrong tokens count against the connection.
   - Each account has its own log, its own Hyperswarm and a quota. Over it, it stops collecting; at twice it, a browser can't sync either. Deleting an account deletes a folder.
   - A rotated key or a new space reaches the node by a new `hold` on the next connection.
   - **Blobs go by hash alone.** What a blob is for lies in sealed events, so a node can't look for them itself. A browser hands over what it makes as it makes it, so a closed tab's pictures stay reachable; when it asks for one that isn't there, the node asks the peers, keeps it and passes it on. They count against the quota and go with the account. A picture made here while the browser is offline goes when it connects, unless the tab closes first.
   - **On the internet** (`storageserver.ts`, `apps/server/src/storage.ts`, `apps/server/deploy/`, `docs/web-deploy.md`): `weave-storage run` serves the page and `/storage`, `weave-storage invite` makes an invitation link. Pages only from the given origins, at most 16 connections per address, a connection silent for 90 s goes (pinged every 30 s), one that doesn't read its 32 MB goes. TLS is Caddy's.
   - **Tried on the real DHT** (7.11.2026, `apps/web/dht-peer.ts` against `weave-storage run`, on one computer): a browser joined a group by a link and read it within 6 seconds, the person on the DHT read its message and picture reference, the picture lay at the node sealed, and what was said while the tab was closed was there after it came back.
   - **Many accounts** (`packages/node/test/storage-load.ts`, on a DHT testnet, each account with two spaces): the accounts' swarms share one DHT node now (`sharedDht`), each with a key and connections of its own. That took 200 accounts from 233 to 193 MB and from 31 to 17 ms an account to come up. What's left is about 420 KB an account, and 370 of it is there without any network: each account's own SQLite and Replica. The rest only pays at many more accounts than a first version has.
   - **Later, not for a first version: spaces, not accounts.** One store and one swarm for the whole node, an account only a list of what it holds: a space shared by five browsers is held once. A person's own space is called `self` for everyone, so in one store it would get a name of its own per account (`self~<account>`), changed where an account's connection meets the store, and deleting an account would count who else holds a space. Not needed while a node has hundreds of accounts, not millions.
   - **Still open:** two computers behind different NATs. Connections per address are limited, attempts per time aren't.
4. **Stores for the browser:** the log is done, tried in a real page (`apps/web`, `npm run dev -w @weave/web`; the store in `apps/web/test/wasmdb.test.ts`). `SpaceStorage`, `SecretStorage` and `LogStore` are synchronous, and OPFS is synchronous only in a Worker, so the whole node runs in a Worker, and the page speaks the same `{id, method, args}` to it that it speaks over `/ws` today.
   - `SqlStore` (`packages/node/src/sqlstore.ts`) is the store without a file: `SqliteStore` puts it on node:sqlite, `apps/web/src/wasmdb.ts` on sqlite-wasm's SAH pool on OPFS, which needs no cross-origin isolation.
   - The page opens a space through a storage node, reads a message live, finds it again after a reload, and gets what was said while it was away. Tried in Chrome (browser-check.ts) and by martl in Safari (8.11.2026); Firefox is open.
   - **One tab at a time:** the pool holds its files, and a second tab would fail. A Web Lock makes it wait: it says the account is open in another tab, and *Use it here* takes it over. The first tab lets go over a BroadcastChannel (the node closes, its Worker ends, the lock goes with it) and says it is elsewhere now, with the same button. Tabs that work side by side are for later.
   - **What it costs** (in the app's Chromium): opening about 3,700 events takes 19 ms, reading them 22 ms. A commit costs about 10 ms, and no PRAGMA changes that (journal modes, `synchronous = OFF`), so a sync takes each batch of 256 as one write (`Replica.batch`): 1.2 ms an event, signing included, instead of 12.
   - **Still to do:** `SpaceStorage` and `SecretStorage` (the account key lies open in the database for now, and the page hands the Worker the space: both go with step 7).
5. **The node in the browser:** done, differently than planned. There is no `WebNode`: the real `WeaveNode` runs in the Worker. It turned out to need little of a computer (15 file calls in `node.ts`, 1.6 MB bundled, before minifying), so a second composition root would only have copied its glue, and every change on main would have had to be made twice. `apps/web/build.ts` answers at the edges instead, from `apps/web/src/host/`:
   - `fs` is a table in the node's own database, so a home works as it is, sealed files included; `path`, `os`, `crypto` and `url` are small stand-ins, tested against what Node says.
   - `SwarmNode` (`host/net.ts`) has the storage node for a network: what the node joins, the storage node joins, by auth keys. A change goes over a second, short connection, since a connection that became a session takes no more requests. Someone else's meeting point isn't handed on, because a storage node announces where a node only looks.
   - `sqlitestore.ts` and `lock.ts` are swapped for the store on OPFS and the Web Lock.
   - Every other module of Node (processes, sockets) is its names, each saying it isn't there when called.
   - What a page may ask is `WEB_METHODS` (`apps/web/src/methods.ts`), one by one; it grows with the screens. The spike's list (22 refused on the everyday screens, 186 in all) is where that goes on.
   - Tried in a real page against a real `WeaveNode` on the other side of a storage node: joining by an invitation link, reading, writing (the other person reads it), members, the feed, a reload (66 ms), and what was said while the tab was away. `apps/web/test/swarm.test.ts` holds the connection's cases against a real storage node. The DHT is a stand-in in `apps/web/dev.ts`; step 3 says where it was the real one.
   - The price: the bundle holds code that can't run here (companies, payments, services). All of it is 0.8 MB gzipped, half of that SQLite, so size isn't the reason to cut. Nothing reaches it from a page that isn't on `WEB_METHODS`. If it matters, the swaps can cut whole modules later.
   - **Friends by contact link** (`apps/web/test/contact.test.ts`, on a DHT testnet): someone else's meeting point goes to the storage node as a topic to look up only, with its proof, so the person's node lets it in and nothing of it is synced. A storage node gives a peer the public events of the account's person and of whoever wrote in what the peer shares, as a person's node does, and asks again when someone new writes there: otherwise a new member's keys never reach the others, and nothing of theirs is taken. Someone reached through a contact link learns the person, not whom the person knows (the test failed on that before the fix). Adding back makes them friends. Tried on the public DHT too (7.11.2026, `DHT=1` in dev.ts): a web account added martl's own Weave by his contact link, and it works.
   - **reconcile:** the daemon runs `node.reconcile()` shortly after new events and every few minutes (admissions, keys, proposals, invitations, images ahead); the Worker didn't, and friends never became friends. Both use `keepReconciling` now.
6. **Hint services in the browser:** done for Unread and Spotlight, tried in a real page: a mention in a group shows "1 new for you" on the group and its channel, with the same component the desktop runs, and a plain message rightly shows nothing. `apps/web/src/service.ts` is `wasmworker.ts` for a browser, and `host/runtime.ts` is the `Runtime`. A hint service calls nothing, so nothing blocks: the host calls of `wasmworker.ts`, which need `Atomics.wait`, aren't needed here.
   - They are transpiled at build time (`buildServices`), since a page has no transpiler. Only what's built in runs, so a project's own hint services don't run on the web yet.
   - The page starts each service's Worker and hands it a channel to the node, because a Worker started from the node's Worker didn't load in the app's browser (a bare error event; it refuses service workers the same way, so it may be only that browser).
   - The price is 12 MB per service, 3.9 MB gzipped, since each carries a JavaScript engine. That wants loading after the first screen, and a long cache. Over localhost: 350 ms until a service is ready, a fold 13 ms; a slow line is untested.
   - The node checks a shipped component's digest by reading its file, and these aren't in the home: the list names a small stand-in file instead, so here the check proves nothing. What the browser runs is what the server sends, as with all of the page's code.
   - `browser-check.ts` tries Unread in a real Chrome (step 8).
7. **Account and passkey:** done, and a real passkey has made an account and opened it again (Windows Hello, 7.11.2026) (`apps/web/src/account.ts`, `lock.ts`, `passkey.ts`; `apps/web/test/account.test.ts` has two browsers and a real person around a real storage node).
   - A way in is a passkey's PRF value or the recovery words. Each gives a key and a token (`lock.ts`). The key opens this browser's home key and the box; the token finds the box, and the storage node keeps its hash.
   - **At rest nothing lies open.** The home key is never written down open: `lock.json` has it sealed once per way in, and the node takes it through `useHomeKey`, the door a company's key service uses. The home is sealed with it as on a computer. So every new tab asks for the passkey (or, without PRF, the words), like a banking app.
   - **A box** at the storage node, one per way in, holds the identity's current root and encryption keys, the keys of the spaces and the identity's key events. It follows the spaces: each new list that goes to the node re-seals the boxes. A new browser makes its own device key and signs it with that root (`WeaveNode.restoreFromKeys`).
   - **A new browser makes its own device key.** Two devices signing with one key would sign different events with the same number, which everyone takes for a stolen key. So it restores from the words, as `weave restore` does.
   - **The price of that, and its limit (13.11.2026):** a passkey opens today's root, so whoever gets the synced passkey and the box can add devices until the person rotates. The box never holds the words, so rotating with them (on a computer, from paper) shuts that out: the next root is made of the words, and nobody but their owner has them. Boxes from before held the words; a browser replaces them the next time it goes online. After a rotation the boxes are out of date: a passkey says so, and the words bring the account again from the person's devices, as from a computer. The words of an account made on a computer work too (`recoverAccount`): one of the person's devices has to be online, and the browser needs an invitation.
   - **A linked browser doesn't pay that price** (`linkBrowser`, `packages/node/src/browserlink.ts`). Someone with Weave on a computer links a browser from Keys & devices → Browsers: the computer issues it a key of its own, as an agent with `*` (so it can't delegate, add devices or rotate, which takes the words), and leaves a handover sealed with a secret at the storage node (`/link/<token>`, in memory, once, 15 minutes). The secret is only in the link, after the `#`, shown as a QR code. The browser opens it, makes a passkey, and is the person: encryption keys, spaces, direct chats; spaces joined later come by the node index, as to an always-on node. What it signs shows as the person, not as an agent. No words come to the browser and no box goes to the storage node, so a stolen passkey or a changed page gets one browser's key, which the computer revokes. A second browser is linked again. Tried in a test of its own (`browserlink.test.ts`) and in a real Chrome (browser-check.ts).
   - A box may hold 256 KB, which is some hundreds of spaces. A larger account would fail to re-seal, and that isn't handled yet.
   - Tried in a real page with the words: locked after a reload, wrong words refused, nothing readable of them in OPFS, and after wiping the site's data the same person came back with a new device key, what was said meanwhile, and a reply the other person read.
   - Keys & devices lists the ways in. A passkey can be added, and removed: its box goes from the storage node too, and the words always stay. Leaving a browser wipes everything of the account there, and the account stays at the storage node. The device's key isn't revoked by that, which takes the words.
8. **Web mode of the UI:** the everyday app runs (`apps/web/src/app.ts`). It's the desktop's renderer as it is: the renderer takes whatever stands in `window.weave`, so the page sets a bridge to the Worker there and loads the renderer after, and every change to the renderer reaches the web. `bridge.web` is what's different: the lock screen (`Unlock` in `keys.tsx`), a passkey on the onboarding screens, and what isn't shown: company accounts, backup files, phones, the keystore, the wallet, keepers, services and agents on Keys & devices, the Desk. On a phone's width it has the mobile layout.
   - Tried in a real page against a real person: a new account, the words, joining, chat both ways, a mention, members, lock and unlock. The passkey there was a stand-in, since the app's browser shows no passkey dialog. A tour of Home, Saved, Inbox, People, Memberships, Keys and a group's chat found only what Keys & devices now hides.
   - `webMethods` (`apps/web/src/methods.ts`) is the phone's list, plus what the screens ask for, minus rooms. A refused method shows in the console.
   - A tour of projects, boards and communities added `artifacts`, `catalog` and `shows` to the list and took Routines off (they need a computer). Their issues and proposals are called with the right arguments by the screens only; a person clicking through them is still to come, as are memberships with payments.
   - **Offline** (`apps/web/src/sw.ts`): the page's files come from the network first and the cache without one, the large ones from the cache first. A locked account opens and reads without a network. The services load at the first `hints`, which the screen doesn't wait for.
   - Someone without a passkey is told so on the words' screen and can add one on Keys & devices. An invitation comes in the address or goes in a field.
   - **Accounts elsewhere** (GitHub): the verifier runs in the browser like Unread, in a Worker of its own, and asks `api.github.com` itself, the only host its manifest names. It waits for GitHub's answer suspended by JSPI (build.ts transpiles verifiers with it), which Chrome and Edge have; a browser without it can't check accounts yet, and says so as "can't be asked right now". A proof is made by hand here, a gist: the one-click proof signs in on github.com, which doesn't answer pages. With an account proven and shared with a project, a web member gets what its GitHub access service hands out, run by its maintainer on a computer as before.
   - **`apps/web/browser-check.ts` runs all of it in a real Chrome**: headless, on a throwaway profile, with Chrome's virtual authenticator with PRF. Making an account with the contacts Weave ships with, a group, Unread, GitHub's verifier asking GitHub, the Settings tab on a phone, a browser linked from a computer, the service worker, leaving the browser, coming back with the passkey alone, a lock, the start without a network. 19 steps, a second tab taking over included; `node apps/web/browser-check.ts`. It isn't part of `npm test`, since it needs a Chrome. The app's own browser can't do this: it loads no service worker, and no Worker from a Worker, with the same bare error, so that may be all that was wrong there.
   - **Still to do:** board views with a client service (`lensBase` points nowhere yet), Firefox.
9. **Rooms (websites), end to end:** a room's tunnel goes through the DHT, and a browser has no DHT and no local port. The storage node carries it, but as a relay of bytes it can't read: what a visitor does on a website is seen by its host only, as in groups and chats. The rejected way was the storage node opening the tunnel itself and serving the website over its own TLS: simpler, but it would read every visit.
   - **The tunnel ends in the browser.** The browser does the Noise handshake with the host itself, with its own key, and the storage node passes the encrypted bytes into the DHT over the socket the page already has (as Hyperswarm's `dht-relay` does: to be checked against the HyperDHT we use). The proofs a host asks of each connection (`live.ts`) are signed in the browser too, so hosts need nothing new.
   - **A website gets an origin of its own:** `<website>.rooms.martl.io`. Apps expect to be at `/`, and a website's code must never be same-site with `web.martl.io`, whose passkeys it could otherwise ask for. A service worker there takes every request the app makes and sends it through the tunnel. The server only serves that small start, never a website's content.
   - **WebSockets** can't be taken by a service worker, and games use them: the start puts a WebSocket of its own in the app's place, through the tunnel too. The hardest part.
   - **In stages:** the tunnel through the relay against a host; HTTP through the service worker; WebSockets; the room's chat and presence.
   - Needs `*.rooms.martl.io` in DNS. Each website's certificate comes by itself; its start is a static file like the page (step 10).
   - **Done (12.11.2026)** at `<label>.weave-rooms.net` (a Cloudflare Worker serves the start): HTTP, cookies, SSE and WebSockets through the tunnel, in Edge and Safari. A tab opened from Weave asks Weave (its opener) for proofs and a single-use relay ticket per tunnel. On a phone's width it opens in a frame over Weave.
   - **iPhone and iPad take the whole window instead:** Safari gives a frame of another origin no service worker. `visitWebsite` makes a key for the visit, asks the node for proofs that carry an `until` (6 hours; hosts reject them after, hosts older than this ignore it) and a relay ticket good again for as long, and hands all of it to the website after `#weave=`, which no server sees. The start keeps it in sessionStorage for reloads; a corner button leads back to Weave, which asks for the passkey at once.
10. **Deploy on martl.io:** Hetzner, Caddy, monitoring, and the law (privacy policy, terms, deletion on request).
   - **The page from elsewhere** (before real users). Today one Hetzner server sends the page and runs the storage node, the front door and a website container: the one most exposed, and whoever takes it changes the code every browser runs. Instead the page is static files at Cloudflare Pages under `web.martl.io` (the name stays, and with it the passkeys), uploaded by GitHub Actions from a tagged commit, and the storage node moves to `storage.martl.io` with its socket and the browser link handovers only. The browser fetches the page from Cloudflare over TLS, and the Hetzner server isn't on that path. Then the page only takes data from the storage node, sealed and signed and checked in the browser, and its CSP allows code from `web.martl.io` only. A storage node taken over can hold data back or send old data, see who writes when, and send garbage the page throws away. It can't steal anything or change code. Changing the page takes martl's Cloudflare or GitHub account (passkey, 2FA). A website's start (step 9) comes from there too.
   - **Hashes watched:** each release build writes the SHA-256 of every file the page serves, published with the release (GitHub, a signed post). A GitHub Action fetches `web.martl.io` every few minutes, compares, and raises an alarm on any difference. Later every desktop Weave checks it too. It sees an attack and doesn't stop one, and code changed for a few people only passes it.
   - **Later, signed releases:** the service worker keeps a release key from the first visit and loads a new version only if that key signed it, warning otherwise. Then not even a taken Cloudflare or GitHub account changes what a returning browser runs. The first visit has to be clean.

## The PRF matrix (https://martl.io/prf.html)

| Browser and provider | PRF at create | PRF at sign-in | Same again, unwraps | Across devices |
|---|---|---|---|---|
| Safari on iPhone (iOS 18.7), iCloud Keychain | yes, with a value | yes | same secret across a reload of the page | not tried yet |
| Windows Hello, on localhost in `apps/web` | yes | yes | a real account made and opened again after a reload | not tried yet |

Safari doesn't answer `getClientCapabilities()` for PRF ("not said") and PRF works there all the same: an account has to try it, not ask first.

## What a new device gets

The passkey opens the sealed secrets at the storage node, the browser syncs from it over one connection, and it reads. No friend has to be online. A browser that evicted its storage gets the same.

## Open

- Is a storage node for one person's spaces also open to a person's own server (a Weave Server they run)? The design allows it; martl.io comes first.
- Sealed envelopes show who signed and when. Whether that's fine for an operator holding many accounts is for the privacy policy, and it may want padding later.
- Quota and price per account.
- Push: the storage node knows something arrived, so a Web Push saying only "there's something new" is possible.
